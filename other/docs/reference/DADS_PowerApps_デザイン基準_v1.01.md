## 1. 目的

デジタル庁デザインシステム（以下「DADS」）の考え方を、Power Apps キャンバスアプリで継続的に実装できる基準へ変換する。

本基準は、次の事項を目的とする。

- 画面ごとの見た目と操作方法を統一する。
- 視認性、操作性、アクセシビリティを一定水準以上に保つ。
- YAML＋Power Fxによる生成・修正を容易にする。
- DADSの更新やPower Appsの仕様変更に対し、影響範囲を限定する。

## 2. 適用方針

### 2.1 基本方針

1. DADSのHTML、React、CSSをPower Appsへ直接移植しない。
2. DADSの原則を、次の3層に変換して適用する。
   - デザイントークン：色、文字、余白、角丸、境界線など
   - UIパターン：入力、ボタン、一覧、通知、ダイアログなど
   - 画面テンプレート：ヘッダー、ナビゲーション、本文領域など
3. Power Appsのモダンコントロールと自動レイアウトコンテナを基本とする。対象パーツに利用可能なモダンコントロールがある場合は、モダンコントロールを第一選択とする。
4. アプリへ実装するソースはYAML＋Power Fxに限定する。
5. HTML、CSS、JavaScript、React、PCFは、個別に承認された場合を除き使用しない。

### 2.2 DADSへの適合表現

Power Appsでは、Web向けDADSコンポーネントの構造、CSS、フォーカス表現などを完全には再現できない。このため、本アプリを「DADS準拠」とは表現せず、「DADSベース」と表現する。

適合判断は、外観の完全一致ではなく、次の原則を満たすことで行う。

- 情報が理解しやすい。
- 操作結果を予測できる。
- キーボードやスクリーンリーダーを含む複数の操作方法に配慮する。
- 色だけに意味を依存しない。
- 十分なコントラストと操作領域を確保する。
- 同じ機能を同じ見た目・同じ操作で提供する。

## 3. 規定レベル

| レベル | 意味 |
|---|---|
| 必須 | 原則として例外を認めない。例外時は理由と代替措置を設計書へ記録する。 |
| 標準 | 通常は採用する。画面要件により変更する場合は一貫性を維持する。 |
| 任意 | 必要性がある場合に採用できる。 |

## 4. 実装アーキテクチャ

### 4.1 デザイン値の管理

色、文字サイズ、余白、角丸、コントロール高さなどを画面ごとに直接記述しない。共通のPower Fxデザイントークンとして管理し、各コントロールから参照する。

次工程で `App.Formulas` に、少なくとも次のトークングループを定義する。

- `Theme.Color`
- `Theme.Font`
- `Theme.Space`
- `Theme.Radius`
- `Theme.Border`
- `Theme.Size`
- `Theme.Breakpoint`

### 4.2 再利用方法

| 対象 | 再利用方法 | 方針 |
|---|---|---|
| 色・文字・余白など | `App.Formulas` | 全画面共通 |
| 単純なボタン・入力欄 | 標準YAMLパターン | データフォームやギャラリー内でも利用可能にする |
| ヘッダー、通知、空状態など | キャンバスコンポーネント | データソースへ直接依存させない |
| データ連携を伴う部品 | 画面側のYAML＋Power Fx | 入出力と責務を明確にする |
| 複雑な業務ロジック | 専用Power Fx | 見た目のコンポーネントから分離する |

コンポーネントライブラリは、非データ依存で安定した複合部品に使用する。Power Appsの制約上、ライブラリコンポーネントはアプリスコープへ直接アクセスさせず、入出力プロパティを介して値を渡す。また、ギャラリーやフォーム内部での利用を前提とする単純部品は、コンポーネント化せず標準YAMLパターンとして管理する。

### 4.3 コントロール選定

1. 対象となるUIパーツにモダンコントロールが用意されている場合は、モダンコントロールを第一選択とする。
2. モダンコントロールで業務要件、アクセシビリティ要件および本書の必須基準を満たせる場合、クラシックコントロールへ置き換えない。
3. クラシックコントロールを使用できるのは、次のいずれかに該当する場合に限定する。
   - 対応するモダンコントロールが存在しない。
   - モダンコントロールに業務上不可欠なプロパティまたはイベントがない。
   - モダンコントロールでは本書の必須アクセシビリティ基準を満たせない。
   - Power Apps Studio上でプレビュー機能として提供され、本番利用の安定性を確保できない。
   - 既知の不具合により、データ登録、表示または操作結果の正確性を確保できない。
4. クラシックコントロールを採用する場合は、対象、理由、代替できない機能および将来の再評価条件を設計書へ記録する。
5. モダンコントロール固有の外観を無理に変更せず、設定可能な範囲で本書のデザイントークンと整合させる。
6. 操作可能なUIをHTMLテキストや画像で擬似的に作らない。
7. コントロール種別を変更した場合も、本書の視覚・操作基準を維持する。

#### 4.3.1 選定順序

| 順位 | 選択肢 | 採用条件 |
|---:|---|---|
| 1 | モダンコントロール | 対応するパーツがあり、業務・アクセシビリティ・安定性の要件を満たす場合 |
| 2 | クラシックコントロール | モダンコントロールで必須要件を満たせず、理由を記録した場合 |
| 3 | 標準コントロールを組み合わせた複合部品 | 単体コントロールでは表現できない場合 |
| 対象外 | HTML、画像、未承認のPCFによる擬似コントロール | 原則使用しない |

## 5. カラー基準

### 5.1 基本パレット

以下をPower Apps向けの確定色とする。色値はDADSのカラートークンを基に選定している。

| 用途 | トークン名 | 色 | 使用条件 |
|---|---|---:|---|
| 画面背景 | `Background` | `#FFFFFF` | 標準背景 |
| 副背景 | `BackgroundSubtle` | `#F2F2F2` | セクション分離、空状態 |
| 面 | `Surface` | `#FFFFFF` | カード、ダイアログ |
| 主テキスト | `TextPrimary` | `#1A1A1A` | 本文、見出し |
| 副テキスト | `TextSecondary` | `#4D4D4D` | 補足、メタ情報 |
| 無効テキスト | `TextDisabled` | `#4D4D4D` | `#E6E6E6` 背景との組合せに限定 |
| 機能境界線 | `Border` | `#949494` | 入力枠など識別に必要な境界線 |
| 強調境界線 | `BorderStrong` | `#666666` | 選択・強調 |
| 装飾区切り線 | `Divider` | `#CCCCCC` | 意味を担わない区切りのみ |
| 主色 | `Primary` | `#0017C1` | 主ボタン、リンク |
| 主色ホバー | `PrimaryHover` | `#00118F` | ポインターホバー |
| 主色押下 | `PrimaryPressed` | `#000071` | 押下状態 |

| リンク | `Link` | `#0017C1` | 下線を併用 |

| 成功テキスト | `SuccessText` | `#197A4B` | アイコンまたは文言を併用 |
| 成功背景 | `SuccessBackground` | `#E6F5EC` | 成功通知 |

| フォーカス内側 | `FocusInner` | `#000000` | 黄色と組み合わせる |

### 5.2 コントラスト

以下を必須とする。

- 通常テキストと背景：4.5:1以上
- 大きな文字と背景：3:1以上
- 入力枠、アイコン、フォーカスなど意味を持つ非テキスト要素：3:1以上
- 主色 `#0017C1` と白：11.10:1
- 主テキスト `#1A1A1A` と白：17.40:1
- 副テキスト `#4D4D4D` と白：8.45:1
- 機能境界線 `#949494` と白：3.03:1
- 成功、エラー、警告は色だけで示さず、アイコンと文言を併用する。

### 5.3 禁止事項

- 薄いグレー文字を本文や入力ラベルに使用しない。
- プレースホルダーだけで入力条件を説明しない。
- 赤、緑、黄だけで状態を区別しない。
- 装飾用の薄い区切り線へ、操作対象の識別を依存しない。

## 6. タイポグラフィ基準

### 6.1 フォント

Power Appsで安定して表示できるシステムフォントとして `Segoe UI` を標準とする。日本語文字は端末の日本語システムフォントによるフォールバック表示を許容する。

DADSの標準であるNoto Sans JPは、Canvasアプリでフォントを一律配布・保証できないため必須としない。

### 6.2 文字スタイル

| 用途 | サイズ | 太さ | 行高の目安 |
|---|---:|---:|---:|
| 画面タイトル | 32 | 700 | 130% |
| セクション見出し | 24 | 700 | 140% |
| 小見出し | 20 | 700 | 140% |
| 本文 | 16 | 400 | 150% |
| 入力ラベル | 16 | 700 | 140% |
| ボタン | 16 | 700 | 120～140% |
| 補足・キャプション | 14 | 400 | 150% |

単位はPower Appsの文字サイズ指定値とする。本文・操作ラベルは16を下回らない。14は補助情報に限定し、入力条件やエラーなど重要情報には使用しない。

## 7. 余白・サイズ・形状

### 7.1 余白スケール

| トークン | 値 | 主用途 |
|---|---:|---|
| `SpaceXS` | 4 | アイコンと文字の微調整 |
| `SpaceS` | 8 | 同一グループ内の近接要素 |
| `SpaceM` | 16 | フィールド間、モバイル余白 |
| `SpaceL` | 24 | グループ間 |
| `SpaceXL` | 32 | デスクトップ余白、セクション間 |
| `Space2XL` | 48 | 大きなセクション分離 |
| `Space3XL` | 64 | 画面上の大区分 |

原則として8の倍数を使用し、4は細かな調整に限定する。

### 7.2 角丸

| 用途 | 値 |
|---|---:|
| 角丸なし | 0 |
| ボタン、入力欄 | 8 |
| カード | 12 |
| ダイアログ、大型面 | 16 |
| チップ、ピル | 高さの50% |

### 7.3 境界線と影

- 通常境界線：1
- 強調・エラー境界線：2
- カードは境界線を基本とし、影を常用しない。
- 影はダイアログ、メニューなど前後関係を示す場合に限定する。

### 7.4 操作領域

- クリック・タップ可能領域は44×44以上を必須とする。
- 見た目が44未満のアイコンでも、親コンテナを含む操作領域は44以上とする。
- 隣接する操作対象の間には8以上の間隔を確保する。

## 8. レスポンシブレイアウト

### 8.1 画面方針

業務PCでの利用を主用途とし、タブレット・スマートフォンでは主要な閲覧と操作が破綻しない構成とする。

| 区分 | 幅 | 画面余白 | 列・配置 |
|---|---:|---:|---|
| モバイル／小型タブレット | 767以下 | 16 | 原則1列 |
| デスクトップ／大型タブレット | 768以上 | 32 | 1列または12列グリッド相当 |

### 8.2 必須ルール

- ルートに自動レイアウトコンテナを使用する。
- コントロールの固定座標配置を画面全体へ多用しない。
- コンテンツ最大幅は1200を標準とし、広い画面では中央寄せする。
- デスクトップの列間隔は32、モバイルの要素間隔は16を標準とする。
- 768未満では、横並びの入力欄とボタンを縦積みへ切り替える。
- 一覧表は、モバイルでは優先項目だけをカード形式で表示し、詳細画面へ遷移できるようにする。
- 重要操作を横スクロールの先に置かない。

## 9. 画面構造

### 9.1 標準構造

画面は原則として次の順序で構成する。

1. アプリヘッダー
2. パンくずまたは現在地表示
3. 画面タイトルと説明
4. 画面全体の通知
5. 検索・絞り込み・主要操作
6. メインコンテンツ
7. 補足、更新情報、フッター操作

### 9.2 ヘッダーとナビゲーション

- ヘッダー高さは64を標準とする。
- アプリ名、現在地、ユーザーが必要とする共通操作を表示する。
- デスクトップでは左ナビゲーションを使用できる。
- モバイルではナビゲーションを折りたたみ、本文幅を優先する。
- 現在地は色だけでなく、文言、太字、下線、選択マーカーなどで示す。

### 9.3 カードとセクション

- 意味のあるまとまりは見出しで区切る。
- すべての情報をカード化しない。
- カード内余白は24、狭い画面では16を標準とする。
- カード同士の間隔は16または24とする。

## 10. コンポーネント基準

### 10.1 ボタン

| 種別 | 用途 | 標準サイズ |
|---|---|---|
| Primary | 保存、実行、確定など主要操作 | 高さ48、最小幅96 |
| Secondary | 編集、再読込など補助操作 | 高さ48、最小幅96 |
| Tertiary | 戻る、キャンセルなど低優先操作 | 高さ48相当の操作領域 |
| Large | 重要な開始・完了操作 | 高さ56、最小幅136 |
| Small | 一覧内の限定的操作 | 見た目36、操作領域44以上 |

必須ルール：

- 1つの画面または明確な操作単位につき、Primaryは原則1つとする。
- Secondaryは同一操作単位で原則3つ以内とする。
- デスクトップの実行・完了操作は右側、戻る・キャンセルは左側を標準とする。
- モバイルでは縦積みとし、画面内で順序を統一する。
- ボタン文言は「実行」「OK」だけにせず、「計算を実行」「変更を保存」のように結果が分かる動詞を使う。
- 無効状態を多用せず、実行できない理由を説明する。可能なら押下時に検証して具体的な案内を表示する。

### 10.2 テキスト入力

入力欄は次の順で構成する。

1. ラベル
2. 必須・任意表示
3. 入力欄
4. サポートテキスト
5. エラーテキスト

必須ルール：

- ラベルを省略しない。
- 必須は `※必須`、任意を明示する場合は `※任意` と表示する。
- プレースホルダーをラベルや入力条件の代替にしない。
- 入力例、形式、文字数などはサポートテキストとして常時表示する。
- エラー文は全角の `＊` で始め、原因と修正方法を具体的に示す。
- 入力欄の標準高さは48。重要入力またはタッチ中心では56、密度が必要な場合のみ36とする。
- 入力内容に応じた幅を設定し、すべての入力欄を機械的に同じ幅へ揃えない。
- 原則としてラベルを入力欄の上へ配置する。
- 読み取り専用値は、入力欄の無効表示ではなく通常テキストとして表示する。
- コピー・貼り付けを禁止しない。
- 検証は原則として送信・保存時に行い、入力途中で過剰なエラーを表示しない。

### 10.3 選択コントロール

- 選択肢が少なく比較が重要な場合はラジオボタンを使用する。
- 多数の選択肢はコンボボックスを使用し、検索可能にする。
- 複数選択であることをラベルまたは説明で明示する。
- 初期値を設定する場合は、業務上安全な値だけを採用する。
- 選択結果を色だけで示さない。

### 10.4 一覧・ギャラリー

- データテーブルよりも、レスポンシブ制御が可能なギャラリーを優先する。
- ヘッダーとデータの列位置を揃える。
- 行の最小高さは48、行内左右余白は16を標準とする。
- 文字列は左寄せ、数値・金額は右寄せ、状態は文言付きで表示する。
- 行全体を選択可能にする場合も、選択状態を色だけで示さない。
- 行内操作は右端へまとめ、操作名またはAccessibleLabelを付ける。
- 0件の場合は空白にせず、理由と次の操作を示す空状態を表示する。
- 読込中、0件、エラーを別の状態として表示する。

### 10.5 検索・絞り込み

- 検索対象をラベルまたは説明で明示する。
- 条件解除を1操作で行えるようにする。
- 適用中の条件と件数を表示する。
- 検索実行方式か即時絞り込み方式かを画面内で統一する。
- 大量データではDataverseへ委任可能な式を優先する。

### 10.6 通知・状態表示

| 種別 | 表示内容 |
|---|---|
| 成功 | 完了した操作と対象を示す |
| 情報 | 状況と次に必要な操作を示す |
| 警告 | 続行時の影響と選択肢を示す |
| エラー | 失敗した対象、原因、修正・再試行方法を示す |

- 一時的な `Notify` だけに重要情報を依存しない。
- 保存失敗、検証エラーなど継続対応が必要な情報は画面内へ残す。
- ステータスチップには「処理済」「未処理」などの文言を必ず表示する。

### 10.7 ダイアログ

- 破壊的操作、取り消せない確定、短い補助入力に限定する。
- タイトル、説明、主要操作、キャンセル、閉じる手段を設ける。
- 破壊的操作のボタン文言には対象と動作を含める。
- ダイアログ表示中は背面操作を防止する。
- 長い入力や複雑な手続は別画面で行う。

### 10.8 アイコン

- Power Apps標準アイコン、または利用条件を確認したDADS公式アイコンを使用する。
- 標準サイズは24、コンパクト表示は20とする。
- アイコン単独操作は、意味が一般的で明確な場合に限定する。
- 操作可能なアイコンにはAccessibleLabelを設定する。
- 装飾アイコンをフォーカス対象にしない。

## 11. 状態設計

操作可能なコントロールには、必要に応じて次の状態を定義する。

- Default
- Hover
- Pressed
- Focused
- Selected
- Disabled
- Error
- Loading

フォーカスはDADSの黄色と黒の二重構造を目標とする。コントロールの仕様上、完全な二重枠を設定できない場合は、黒2以上のフォーカス枠を最低条件とし、周辺コンテナで黄色の外側強調を追加できる場合は追加する。

無効状態は最小限とし、状態の意味を色の薄さだけで伝えない。

## 12. アクセシビリティ基準

以下を必須とする。

### 12.1 キーボード操作

- 操作順は画面の視覚順・読み上げ順と一致させる。
- 操作対象は論理的なツリー順で `TabIndex = 0`、非操作・装飾要素は `TabIndex = -1` を基本とする。
- 1、2、3のような正の番号でフォーカス順を手動管理しない。
- フォーカス位置を視覚的に確認できるようにする。
- キーボードだけで主要機能を完了できるようにする。

### 12.2 読み上げ

- アイコンボタン、入力、検索、閉じる操作などへ具体的なAccessibleLabelを設定する。
- `Tooltip` をAccessibleLabelの代替にしない。
- 画面タイトル、セクション見出し、入力ラベルの階層を視覚的・意味的に一貫させる。
- エラー発生箇所とエラー内容を読み上げ利用者が把握できるようにする。

### 12.3 視認性

- 5章のコントラスト基準を満たす。
- 文字拡大や狭い画面で、文字や操作対象が重ならないようにする。
- 色、形、位置のいずれか1つだけに情報を依存しない。
- 動画・点滅・過度なアニメーションを業務UIで使用しない。

### 12.4 入力支援

- 入力エラー後もユーザーが入力した値を保持する。
- エラーを画面上部と対象項目付近の両方で把握できるようにする。
- 同じ情報を不必要に再入力させない。
- 日付、金額、時間などは入力例と単位を示す。

## 13. 業務アプリ固有基準

### 13.1 金額・時間・件数

- 金額は桁区切りを行い、必要に応じて `円` を表示する。
- 時間と時刻を混同しない表記にする。
- 0、未入力、該当なしを区別して表示する。
- 計算前の値と計算結果を視覚的に区別する。
- 丸め、端数、日割りなど計算根拠を確認できる導線を設ける。

### 13.2 実行・保存・確定

- 「計算」「保存」「確定」を別の操作として扱う場合は、状態と影響を明示する。
- 二重実行を防止し、実行中であることを表示する。
- 完了後は、対象職員、対象年月、処理件数、成功・失敗件数を確認できるようにする。
- 失敗時は成功分と失敗分を区別し、再実行範囲を明示する。

### 13.3 個人情報

- 職員情報は業務に必要な項目だけを表示する。
- 一覧での不用意な全面表示を避け、詳細表示へ分離する。
- コピー、出力、取込などデータ移動を伴う操作は明示する。

## 14. 命名規則

コントロール名は英数字を使用し、役割と内容が分かる名前とする。

| 種別 | 接頭辞 | 例 |
|---|---|---|
| Screen | `scr` | `scrEmployeeSearch` |
| Container | `con` | `conSearchConditions` |
| Label／Text | `lbl` | `lblPageTitle` |
| Text input | `txt` | `txtEmployeeName` |
| Button | `btn` | `btnRunCalculation` |
| Gallery | `gal` | `galEmployees` |
| Icon | `ico` | `icoSearch` |
| Component | `cmp` | `cmpAppHeader` |
| Form | `frm` | `frmEmployee` |
| Combo box | `cmb` | `cmbDepartment` |

`Button1`、`Label3`のような自動生成名を完成版へ残さない。

## 16. 適合確認チェックリスト

### 16.1 デザイン

- [ ] 色、文字、余白、角丸を共通トークンから参照している。
- [ ] Primaryボタンが操作単位ごとに原則1つである。
- [ ] 本文と操作ラベルが16以上である。
- [ ] 操作領域が44×44以上である。
- [ ] 意味を持つ色の組合せが所定のコントラストを満たす。
- [ ] 狭い画面で横並びが縦積みへ切り替わる。

### 16.2 入力・操作

- [ ] すべての入力欄に常時表示ラベルがある。
- [ ] 必須・任意、入力形式、単位が明確である。
- [ ] エラーが原因と修正方法を示している。
- [ ] 読込中、0件、成功、失敗を区別している。
- [ ] 実行ボタンの文言から結果を予測できる。

### 16.3 アクセシビリティ

- [ ] キーボードだけで主要操作を完了できる。
- [ ] フォーカス位置を視認できる。
- [ ] AccessibleLabelが必要な操作に設定されている。
- [ ] 色だけで状態を伝えていない。
- [ ] スクリーンリーダーで主要な読み上げ順を確認した。
- [ ] 200%相当の拡大または狭い幅でも操作不能にならない。

### 16.4 Power Apps

- [ ] 対応するモダンコントロールがあるパーツでは、モダンコントロールを第一選択としている。
- [ ] クラシックコントロールを使用した箇所は、採用理由と再評価条件を設計書へ記録している。
- [ ] データ量を考慮し、Dataverseへ委任可能な式を使用している。
- [ ] データソースをコンポーネントへ直接埋め込んでいない。
- [ ] 固定座標ではなく自動レイアウトを基本としている。
- [ ] YAMLを貼り付けた後、Studio上で警告とエラーがない。
- [ ] PC、タブレット、スマートフォン相当幅で確認した。

## 17. 例外管理

本基準を満たせない場合は、画面設計書または詳細設計書へ次を記録する。

1. 対象画面・コントロール
2. 満たせない基準
3. Power Appsまたは業務上の制約
4. 採用した代替措置
5. 利用者への影響
6. 将来の見直し条件

アクセシビリティの必須基準を外す例外は、単なる見た目上の都合では認めない。

## 18. バージョン管理

- 本版はDADS β版 v2.18.0を参照したPower Apps向け基準 v1.01とする。
- DADSは更新されるため、参照版を固定して記録する。
- DADS、Power Appsモダンコントロール、Canvasコンポーネントの仕様が更新された場合は影響評価を行う。
- 色、サイズ、操作原則を変更する場合は本書を改版し、アプリ側のテーマを同時に更新する。
- 既存画面へ一括反映する前に、スタイルギャラリー画面で視覚・操作確認を行う。

## 19. 次工程

本基準の確定後、次の順で実装する。

1. `App.Formulas` 用のデザイントークンをPower Fxで作成する。
2. 共通コントロールの貼り付け用YAMLを作成する。
3. 全状態を確認できるスタイルギャラリー画面を作成する。
4. PC幅・モバイル幅・キーボード・読み上げの受入確認を行う。
5. 業務画面へ順次適用する。
