# テスト方針

> 対象アプリ：共通（自動テスト／ハンドメイド）

文書版：v1.00／作成日：2026-09-13
対象：非常勤職員マスタ検索・通勤手当認定簿／B案＋職員検索サイドバー開閉
基準：アプリv1.11、要件・基本設計・詳細設計v1.03
状態：テスト設計。自動化環境・テストコードの構築、実機試験は本更新では実施していない。

詳細な手順、データ、期待値、ケースIDは[テスト仕様書](test-specification.md)に定める。本書は「何を、いつ、どの証拠で合格とするか」の共有正本とする。

## 1. 目的

ユーザーが毎回「テストして」と指示しなくても、YAML／Power Fxの変更ごとに規定の試験を選定・実施・記録する。特に、次の再発を防ぐ。

- 検索ボタンを押しても架空データが表示されない。
- 数式の独自評価では正しくても、入力値、イベント、ギャラリー、表示状態がPower Apps上では連動しない。
- 表の文字が左端に重なり、右端や下端が欠ける。
- 未対応プロパティ（PA2108）やPDFViewerの親制約（PA2131）で貼付できない。
- 前の職員の履歴・帳票・PDFを別の職員のものとして表示する。
- PDF表示、生成、保存を混同し、保存されていないのに成功扱いする。

静的検査、ローカル数式モデル、HTML等による配置モデル、生成AI画像を、Power Appsの動作試験の代用にしない。

## 2. 対象範囲と完成範囲

| 区分 | 対象 | 完成と判断する範囲 |
|---|---|---|
| CORE | 起動、架空データ、検索、一覧、ページ、職員選択、基本9項目、6履歴、給与詳細、0件、開閉、文字切替、モーダル、TSV | 公開アプリで実操作・表示内容を確認 |
| REPORT | 認定簿2枚、職員・認定ID・金額整合、PDF生成・保存・失敗復帰 | 実際に生成・取得したファイルを内容と画像で確認 |
| ACCESS | キーボード、フォーカス、状態表現、拡大、コントラスト、読み上げ | 自動検査と支援技術による確認を区別 |
| DELIVERY | Source Code構造、2形式同期、差分適用・復元、導入再現 | 対象ハッシュと導入済み版の対応を確認 |
| 対象外 | 実職員データ、本番Dataverse、法定給与・税・保険計算、正式XLSX、スマホ版画面の全面対応 | 別要件・別試験で追加。現行合格から推定しない |

スマホは開発指示・結果確認の端末であり、今回の業務画面の主試験対象はPCサイズ。職場の実データ、組織の資格情報、内部URLを個人環境・公開GitHubへ持ち出さない。

## 3. 根拠と現状の扱い

正本は[要件R01～R14](../requirements/requirements.md)、[基本設計](../design/basic-design.md)、[詳細設計](../design/detailed-design.md)、[B案](../design/design-system.md)。旧HTML設計は業務項目の参考で、旧接続仕様を自動化へ持ち込まない。

v1.11についてユーザーから「検索してもデータが表示されない」と報告を受けている。これは未解決不具合`BUG-SEARCH-001`として扱う。実行版・環境の厳密な照合と原因再現は未実施。既存の[68件のローカル検査記録](RESULTS.md)は保存するが、実機合格や不具合解決の根拠にしない。

現行通勤データには認定IDがなく、共通認定簿サンプルとの金額整合も未完了。正式用紙も未決。この範囲はREPORT完了を妨げる残件であり、試験から黙って除外しない。

## 4. テスト層

| 層 | 実施内容 | 証明できること／できないこと |
|---|---|---|
| L0 文書・ソース検査 | YAML重複キー、参照、コントロール／親制約、差分、機密混入、項目台帳 | 既知違反を検出。対象環境の公式インポート成功は証明しない |
| L1 ローカルモデル | 限定Power Fx評価、抽出期待値、状態・寸法式 | 対応した式の推定結果。公式型検査・入力イベント・実描画ではない |
| L2 Power Apps受入 | 対象環境で導入、App checker、保存・公開、版照合 | 実際の導入と公式環境の診断。実操作の成功とは別 |
| L3 公開アプリE2E | ブラウザで入力・クリック・選択・スクロールし、可視内容を照合 | 実行時の機能。内部変数や成功通知だけでは合格にしない |
| L4 表示・帳票検査 | 実画面キャプチャ、配置検査、PDFのページ数・差込・画像比較 | 視覚的な欠損と出力実体。人間の疲労感や全支援技術の使いやすさを完全には代替しない |

将来のL3はMicrosoftの[Power Platform Playwrightサンプル](https://learn.microsoft.com/en-us/power-platform/developer/playwright-samples/overview)を参考にする。これは採用方針であり、このリポジトリに実行基盤が構築済みという意味ではない。

## 5. 実施タイミング

| タイミング | 必須試験 |
|---|---|
| YAML／Fxの変更ごと | L0、対応範囲のL1、変更影響ケース、スモークSMK-01 |
| 画面公開・試作版配布前 | L2、SMK-01、変更領域のE2E、8条件のレイアウト検査 |
| リリース候補 | 対象プロファイルの全ケース、独立した新規セッションで3回連続スモーク |
| 差分パッチ | 差分適用／復元試験＋変更部品の親子・参照先・下流機能の回帰 |
| 実行基盤構築後 | 上記を自動実行。定期回帰は原則毎日1回を設定候補とする（今回予約しない） |
| コントロール版・ブラウザ・認証・接続設定変更 | 関連ケースと全スモーク。変更が広範囲なら全回帰 |

環境がない期間もL0/L1とテストコード準備をWorkが担当し、L2～L4はNOT_RUNまたはBLOCKEDで報告する。手作業をユーザーに依頼するときは未実施ケースIDと具体的手順だけを渡す。環境構築後は通常E2Eを自動実行に置き換える。

## 6. 合否と出荷ゲート

| 結果 | 定義 |
|---|---|
| PASS | 指定版・データ・環境で全期待値と必要証跡を確認 |
| FAIL | 実行できたが期待値に不一致。未実装の必須機能も該当 |
| BLOCKED | 認証、環境、fixture、未決仕様等により実行・判定できない。理由と解除条件を必須記録 |
| NOT_RUN | 未実行。実行予定があるだけではPASSにしない |
| NOT_APPLICABLE | 承認済みの対象外。承認根拠と要件IDが必要 |
| FLAKY | 同じ入力・版で合否が変動。再実行成功だけで解決しない |

- CORE合格：CORE/DELIVERY対象の必須ケース全件PASS、必要な表示・操作アクセシビリティ検査完了、重大・高不具合0、スモーク3回連続PASS。未構築のE2Eがある間はCORE合格としない。
- REPORT合格：COREに加え認定ID・金額・PDF実体・保存・失敗系全件PASS。未接続なら「COREのみ合格／REPORTはBLOCKED」と明記する。
- 全体完成：対象の全必須ケースがPASSで、未決事項が解消し、ユーザーが業務・視認性を受入。アクセシビリティ自動検査だけで全面準拠を宣言しない。
- 既知のNGは版別に残す。修正後に該当ケースとスモークを再実行し、解決証跡を関連付ける。
- 合格率はPASS／対象ケース数で示し、FAIL/BLOCKED/NOT_RUN/FLAKYを分母から除外しない。パラメーター展開後のケース数を使用する。

不具合重大度：致命的＝別職員帳票・情報漏えい・データ破壊、高＝検索不能・全文判読不能・PDF必須機能不能、中＝回避可能な部分崩れ、低＝機能を阻害しない軽微な装飾差。致命的・高の残存を許容して「完了」と報告しない。

## 7. 自動化の信頼性

1. 期待値は仕様書と独立fixtureから作る。被試験YAMLの検索式を再利用して期待値を生成しない。
2. 初期化ボタン、ClearCollect、内部変数書換えで起動・検索不具合を隠さない。復旧ボタンの試験は別ケースにする。
3. UI操作後、件数・職員番号集合・選択職員・可視行・関連履歴を照合する。クリック成功、通知表示、DOM存在だけを合格にしない。
4. 固定sleepではなく期待状態を期限付きで待つ。タイムアウトは失敗または環境障害として記録し、黙って延長しない。
5. 各ケースは新規アプリセッションと固定データから開始する。認証状態だけ再利用し、アプリ変数を持ち越さない。テスト用状態設定は専用fixtureの読込に限定する。
6. 画面の旧版を試験していないことを、公開版ID・展開ログ・ソースハッシュ・画面版表示で照合する。
7. スクリーンショット基準を失敗のたびに自動更新しない。意図したUI変更は差分をレビューして承認する。
8. 不具合を意図的に入れた検査器検証も行う。検索OnSelect無効、Items空、重なり、旧PDF残留を検出できることを確認する。
9. PDFはモーダルの画像だけではなく、実際の生成バイト列／保存ファイルを検証する。
10. 自動修復は1要求あたり原則3回まで。同じ失敗の反復、仕様矛盾、認証・権限問題では停止し報告する。認証回避や本番変更を行わない。

## 8. 画面・アクセシビリティ

1366×768／1920×1080 × 標準／大文字 × サイドバー展開／折りたたみの8条件を最低セットとする。CSS viewport、アプリ実描画寸法、OS倍率、ブラウザ倍率、DPR、フォントを記録する。

文字の重なり・重要値の欠け・ボタンの遮蔽・最終列へ到達不能は不合格。表の横スクロールは許容し、画面全体の極端な縮小や列削除で対処しない。幾何学検査は罫線・選択マーカー等の意図した重なりを例外台帳に登録する。非表示要素を測定対象に含めない。

文字色・背景色、キーボード操作、フォーカス、200%拡大を試験する。読み上げと日本語の疲れにくさは、人による確認が残る領域として独立記録する。[WCAG 2.2](https://www.w3.org/TR/WCAG22/)を参考とし、表等の二次元配置の例外と、検索操作部の使いやすさを分けて確認する。

## 9. 証跡とセキュリティ

各実行にrun ID、日時、アプリ版・公開版、Git SHA、YAML SHA-256、fixture版、環境別名、ブラウザ版、viewport、ケースID、期待値、実値、結果、証跡、欠陥IDを記録する。ログ・動画・ダウンロードは実行ID別に保存し、再実行で上書きしない。

公開GitHubには仕様、架空fixture、サニタイズ済み結果要約を置く。認証storage state、秘密鍵、トークン、署名URL、実職員データ、機密を含むブラウザtraceは格納しない。生証跡は非公開保管先を使用し、保持期間は暫定30日、リリース証跡90日を初期提案とする。環境構築時に費用とアクセス権を確定する。

スマホ向け結果要約は「対象版／CORE・REPORT結果／失敗ケース／画像リンク／残件／次の処置」の順とする。Workがセッション外で無期限に監視・修正する前提にせず、外部自動実行と結果確認の責任を分ける。

## 10. 運用・変更管理

Workが試験設計、実装時の自動実行、結果整理、一次レビューを担当。ユーザーは業務判断、未決仕様決定、最終受入を担当する。通常の既定試験を実行するための都度指示は不要。

仕様変更では先に要件IDと期待結果を更新し、その後に実装・テストコードを修正する。不具合をPASSにするための期待値変更は禁止。v1.12以降は[コントロール差分方針](../operations/control-diff-policy.md)に従い、完全版と差分配布物の両方を検証する。

今回は文書2点と導線・現状記録だけを更新する。環境契約、Actions設定、Power Apps公開、YAML修正、既存ファイル削除は実施しない。
