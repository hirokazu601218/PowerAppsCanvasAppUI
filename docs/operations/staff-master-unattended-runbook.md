# 職員マスタ 無人修正・テスト公開の運用手順

> 対象アプリ：自動テスト専用

更新：2026-09-16。v1.12でテスト公開運用を開始。構築と受入は [Issue #7](https://github.com/hirokazu601218/PowerAppsCanvasAppUI/issues/7)、v1.14の配置とREADME更新は [Issue #23](https://github.com/hirokazu601218/PowerAppsCanvasAppUI/issues/23) に記録する。

## 1. 指示から成功版まで

開始前に、指示を受けた同じWorkへ今回の工程一覧を最大10工程で提示する。提示後はユーザーの追加承認を待たずに開始する。通常のアプリ修正は次の10工程を使用し、文書・基盤だけの変更は対象範囲に応じて10以内にまとめる。開始後の番号は維持し、修復・再実行は該当工程の試行として記録する。

| 工程 | 内容 | 主な確認根拠 |
|---:|---|---|
| 1 | 要件・現状確認と工程提示 | 指示、STATUS、対象と受入条件 |
| 2 | Issue・作業ブランチ・PR作成 | IssueとPR、指示自体の承認記録 |
| 3 | 設計・ソース・文書修正 | 対象差分と累積マニフェスト |
| 4 | 追加テスト準備・静的検査・必要な旧版確認 | 単体結果、旧仕様期待値の検証 |
| 5 | ビルド・認証・テスト環境への反映・公開 | Actions、build/auth/import/publishの結果 |
| 6 | 公開内容の読戻し照合 | readback結果、固定環境・App ID |
| 7 | 指示別追加テスト | change_test結果、版・表示・操作証跡 |
| 8 | P0回帰テスト | p0結果 |
| 9 | main統合・成功版確定 | 試験済みSHA、PR、注釈タグ |
| 10 | README等の更新・同じWorkへの工程別結果報告 | mainの文書、文書PR、全工程の結果表 |

実装は`powerapps/canvas-v3/Src/`を変更し、`automation/change.json`へ指示・承認の根拠と累積変更を記載する。`before`は元msappの値、`after`は公開予定値とし、既存合格版の変更も含める。独立した追加テストを用意し、新locatorは旧成功版の期待値でも検証する。既存P0を削除・緩和しない。

配布する工程5でのみ`automation/run.json`を`mode: release`、今回のIssue、未使用request ID、`approved: true`へ変更してpushする。文書・名称設定だけの今回の依頼では変更せず、配布しない。工程7冒頭でPlayerの版を最大90秒の再読込み付きで確認し、観測版を保存する。APIのReadyだけでUIの版一致とはみなさず、旧版での合格や機能テストのretryは行わない。

失敗時は該当工程で原因指紋と対応差分を記録する。指示範囲内に未試行の対応策があれば修復し、新request IDで再実行する。新対応策がなければ停止し、配布後の未知の失敗は実行開始時に固定した合格版へ復元して追加テストとP0で確認する。失敗した要求のPRは閉じ、ブランチは保持する。復元成功を元の要求の成功とは扱わない。

工程9は7ゲート合格後に候補SHAを固定してmergeする。最終化処理が同一tree、最新run、全ゲート、固定App ID、公開状態、Solutionハッシュを照合する。続けて`readme_release.prepare`でREADMEを更新したコミットを作り、`release_snapshot.verify`で版・リンク・検証run・READMEハッシュと、テスト済みソースからの差分がREADMEだけであることを照合する。合格後にそのコミットへ成功タグを作る。

工程10で`readme_release.publish`が工程9で用意した専用ブランチをPR経由でmainへ統合する。ActionsのPR作成が許可される場合は統合まで実行する。現設定の既知の禁止だけは`PENDING_WORK_PR`とブランチ/SHAを`readme-update.json`・Issueに残し、Workが追加確認なしに生成差分・タグとの一致を確認してPR統合を継続する。未知のエラーは停止し原因を確認する。タグ内とmainのREADMEの版・リンクの確認まで工程10を成功としない。権限設定を緩めず、文書更新でアプリを再配布しない。

### Workでの進捗・結果表示

- 工程切替時に「現在：工程5／10 テスト環境への反映・公開」の形式で提示し、直前工程の結果と次の確認事項を短く伝える。長時間の作業中も約60秒を目安に更新する。
- WorkがActionsのjob/step、Issueの試行記録、取得できるログを確認して報告する。ランナーからWorkへ直接通知する仕組みや、Workが動いていない間の継続監視を実装したという意味ではない。
- Actionsの1stepが工程5～8をまとめて実行する場合、内部工程を確認できる証跡がなければ「工程5～8を含む処理が実行中、内部の現在位置は確認中」と表示する。時間経過だけで次工程へ進めたり、架空の進捗率を付けたりしない。状態取得失敗時は最終確認時刻と未確認範囲を示す。
- 終了・停止時は、最初の一覧と同じ番号・名称の全工程を「工程／結果／根拠・補足」の表で同じWorkへ報告する。結果は成功・失敗・対象外・未実施を区別する。実行中・確認中を成功に換算しない。
- 失敗後の修復は「成功（初回失敗→修復後成功）」等と試行履歴を残す。前工程の失敗で動かなかった後続工程は未実施、今回配布しない等の判断は対象外とし、理由を示す。復元結果と元要求の成否は別に記載する。
- Issue・PR・Actions・版・公開状態・残件へのリンクを付ける。文書・基盤のみの場合はアプリ公開・E2E・P0を対象外と明記し、前回の合格を今回実行したように報告しない。

指示の承認は範囲内の修復、テスト、テスト用公開まで有効。基準・本番、課金、権限、接続の変更は別の承認範囲となる。

## 2. 編集方式と対応範囲

指定一覧名は`config/apps/staff-master.json`の`display_name`（自動開発_職員マスタ検索）とする。Power Apps実体の手動改名はユーザー担当で、Workは完了を推測しない。対象は表示名でなく固定環境ID・App IDで識別する。README生成と配布用meta.xmlを指定名へ揃え、通常配布・旧タグ復元のpack時も現在の指定名を使う。旧タグ・元msapp・スキーマ名・内部111部品ID・画面内の版表示は改名しない。過去の実行記録には当時の旧名を残す。今回の名称・報告ルール更新では配布要求を起動しない。

`scripts/automation/bridge.py` は既存コントロールの既存プロパティを、承認済み変更前後値と照合してactive YAMLと実行用ルールへ同期する。元msappのハッシュとソース全体も検査し、記載外の変更やSolutionの接続・部品変更を拒否する。

これは現行Canvasの互換ブリッジであり、任意のPower Fxや新規コントロールを一般コンパイルする機能ではない。新規画面、構造変更、接続、未対応プロパティは配布前に停止する。追加対応は別途設計・承認し、実際の読戻しと変更テストで成立を確認する。

アプリ固有ID、URL、元msappハッシュは `config/apps/staff-master.json`、承認済み変更は `automation/change.json` に分離した。他アプリの追加には別configと追加受入が必要で、現在は職員マスタだけを配布する。

## 3. 原因と対応策の記録

- 原因指紋：テストケースID＋失敗工程＋正規化エラーのSHA-256。UUID・時刻・一時パス・ANSI装飾だけを正規化し、期待値等の意味を残す。
- 対応策識別：実際の編集内容のSHA-256。名称だけ変えても既試行として扱う。
- 同じ原因が2回でも、新しい実質的な対応策があれば続行できる。同じ対応策の単純反復は行わない。
- 認証、範囲違反、復元失敗はアプリ修復ループへ入れない。GitHub実行マシン未取得等の基盤障害もアプリ不具合と分離する。
- `attempts.jsonl` と `result.json` が機械可読な記録。各試行の概要は同じIssueへ残す。別runへ進む前にWorkが既存Issueの試行台帳を照合する。
- 失敗工程は最後に実行した工程ではなく、不合格ゲートから記録する。変更テスト失敗・P0成功をP0失敗と表示しない。復元テストが不合格の場合も、復元版の各ゲート結果を`restoration.gates`へ保持する。
- 構築時の既知不具合試験では、期待値を固定したまま宣言済み修復をランナー内で自動適用する。未知の不具合の分析はWorkが担当する。

## 4. 合格版と復元

成功時だけ0.01加算する。最初の成功タグは `v1.12`。ソース上の候補版表示は成功採番を意味しない。

正本はmainと成功タグ。成功タグの注釈にrun、候補commit、main commit、環境、App ID、公開版、Solutionハッシュ、全ゲート結果を永久保存する。次回実行時は同じ対象の有効な成功タグを選び、なければ `automation/release.json` の `last_good_commit` を使う。初期合格commitは `260819a4fa30c4d8c8dcd02acc626c26d7823697`。`automation/release.json` は合格確定後に更新する控えであり、正本の受領記録はタグの注釈に保持する。

手動回復が必要な場合は、合格タグからブランチを作り `automation/run.json` を `mode: restore` にして実行する。基準commitへのcheckout→再構築→同じ隔離URLへのインポート→公開→読戻し→表示確認＋P0で復元を確認する。

`RESTORE_FAILED` の場合は新たなアプリ変更を止め、元エラーと復元エラー、対象App ID、復元commit、最後の公開情報をIssueへ提示する。ワークフローの強制キャンセル、ランナー消失、ジョブ全体のタイムアウトでは終了処理を保証できないため、別の `restore` 要求を実行して確認する。キャンセル後の画面状態を推測で合格にしない。

## 5. 認証・証跡・旧ワークフロー

配布IDはGitHub OIDCを使用し、Client Secretは作らない。専用テスト利用者の認証は既存GitHub EnvironmentのSecretsを使用する。期限切れ等ではWorkが原因を記録し、所有者が既存Secretsを更新する。パスワード・認証状態・証明書をIssueやartifactへ出力しない。権限やMFAを自動変更しない。

スクリーンショット・動画・トレース、実行ログ、パック、読戻しは14日保持。Issue概要とタグの受領記録は保持期限なし。テスト利用者のCanView共有は既存設定を利用する。

認証が配布前に失敗した場合はアプリ不具合と分ける。公式認証ライブラリが保存した`*-failed-*.png`だけを専用artifactへ1日保持し、Cookie・storage state・トークン・資格情報は収集しない。2回連続して同じ認証画面で停止したら単純な再実行を止め、`staff-master-auth-diagnostics.yml`で同じID・設定・URLの認証だけを診断する。このワークフローにはアプリのbuild/import/publishやOIDC権限を含めない。診断結果と停止画面を確認して次の処理を決める。MFA・条件付きアクセス・資格情報を自動変更しない。

通常の配布は `staff-master-transaction.yml` のみを使う。`phase2-source-reconstruction.yml` は旧実証用でpush起動を廃止した。旧phase1.5系は調査記録として保持し、通常運用で再実行しない。隔離環境を書き換える現行・復元処理は共通concurrency groupで直列化する。

## 6. 公開版と旧GitHub版の差分

旧 `src/staff-master/scrStaffMasterSearch_v1.11.pa.yaml` は356個のプロパティ保持ノード、公開アプリ由来activeソースは360個で、355個の名前を共有する。公開版にはStudioの画面と外側コンテナーがあり、既定値の省略や式の差もある。文字列比較の差をすべて機能差とは判定しない。

詳細は [機械可読差分](staff-master-baseline-comparison.json) にプロパティ名と値のハッシュで保存した。採用判断は既に承認された「P0合格済み公開アプリを基準」とし、旧ソースは履歴・参照として保持する。旧版を混ぜて再配布しない。初回v1.12は版表示だけの変更だったが、現在の累積差分は`automation/change.json`で管理する。

## 版表示の整合と既存v1.14の訂正（Issue #29）

成功タグのschema 2受領記録では、`main_commit`は検証済みの統合commit、`release_commit`はREADME訂正を含むタグ対象commitとする。候補treeと検証済みtreeの一致、release_commitまでの差分がREADMEだけであること、READMEハッシュ・版・リンク・検証run・全7ゲートを機械検証する。復元版の選定時にも検証し、不正なタグを採用しない。通常フローで既存タグを上書きしない。

v1.14の既存不整合に限り、専用ワークフローで元注釈タグを`archive/v1.14-before-readme-fix`へそのまま保全し、READMEだけを直したコミットへv1.14を訂正する。元タグobjectを固定したforce-with-leaseとatomic pushを使い、競合時は保全・訂正とも停止する。アプリソース・公開版・元の検証証跡は変更しない。再実行時は訂正済みタグと保全先を検証するだけとする。保全タグは成功版の採番・復元候補から除外する。
