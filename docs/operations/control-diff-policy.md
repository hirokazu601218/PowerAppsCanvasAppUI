# コントロール単位YAML差分配布方針 v1.00

適用開始：v1.12。基準となる完全版：v1.11。作成・検査・レビューはChatGPT Sol Workで行う。

## 1. 結論と制約

**変更が生じたコントロール単位での配布は可能。** ただし、Studioの「コードを貼り付け」は既存コントロールへの差分マージではなく、新しいコントロールとその子を作成する機能である。コード表示は読み取り専用。既存コントロールと同名のYAMLをそのまま追加しても、安全な上書きにはならない。[Microsoft：code view](https://learn.microsoft.com/en-us/power-apps/maker/canvas-apps/code-view)

このため「差分配布」と「Studioへの適用」を以下のように分ける。`git diff`の`+`/`-`付きテキストをStudioへ貼らせない。

## 2. 最小単位

| 変更 | 配布・適用方法 |
|---|---|
| ボタン等、子を持たない部品 | 変更後のそのコントロールの完全なSource Code形式YAML。全画面は配布しない |
| コンテナの配色・幅・Visibleだけ | 最少トークンで済むよう対象プロパティとPower Fxを配布し、数式バーで更新する方法を優先。YAMLによる置換を選ぶ場合は子を含む完全なサブツリーが必要 |
| 子の追加・削除・並び替え | 最小の共通親コンテナ＋必要な全子コントロール。兄弟の参照式変更が必要なら同じパッチへ含める |
| 画面OnVisible／App.Formulas等 | 該当プロパティのPower Fxを別ファイルで提供し、貼る場所・既存式との追記／置換の別を明示。コントロールYAMLの貼付では適用されない |
| PDF Viewer・画面直下部品 | 親をScreenとして明記。GroupContainerのChildrenに混ぜない |
| 広域構造変更・多数の依存変更 | 例外として広いサブツリー／画面全体を配布。必要理由・影響範囲を説明する |

コントロールのYAMLは`Control`、必要な`Properties`、必要なら`Children`を持つ自己完結した部品定義とする。「変更したプロパティだけ」のYAMLを完全な貼付コードと呼ばない。

## 3. GitHub構成

```text
src/staff-master/
  scrStaffMasterSearch_v1.11.paste.yaml     基準の完全版
  scrStaffMasterSearch_v1.11.pa.yaml        同じChildrenを持つ管理版
  patches/
    README.md
    v1.12/                                実際に変更したときだけ作成
      manifest.json
      INSTALL.md
      controls/<control-name>.paste.yaml
      properties/<control-name>.<property>.fx   必要な場合のみ
```

新しい完全版（例：v1.12の2形式）は、正本の該当ノードに差分を適用して機械的に同期する。人／LLMが全画面を最初から書き直さない。会話ではパッチへのリンク、変更点、適用順のみ案内し、完全版の全文を再掲しない。差分適用結果と新しい完全版が同じツリーであることを検査する。

v1.11のコントロール名・変数名・コレクション名の`111`は、以降は互換性のため固定する。v1.12になっても`btnSidebarToggle111`等を一括改名しない。版はファイル名、manifest、画面の版表示、変更履歴で管理する。安定IDを変更する必要がある場合だけ参照更新と移行手順を追加する。

旧完全版の整理は新版の実機確認後に行う。削除した版はコミットIDから復元できるように記録し、無関係の資料・別画面・画像様式を削除しない。

## 4. manifestに必須の情報

- `baseVersion`／`targetVersion`、基準コミット、対象完全版のSHA-256。
- 対象画面、コントロール名、親の完全パス、操作（追加／置換／削除／プロパティ更新）。
- 前後の兄弟・表示順、ギャラリーのTemplate内かどうか、自動／手動レイアウトの別。
- 他コントロール、変数、コレクション、App/Screenプロパティ、画像、フローへの依存。
- 適用順、期待結果、実施済み検査／未実施検査、復元元コミット。
- 初期値の変更、状態リセット、対象データへの影響があるか。

基準版や実機コードが違う場合はそのまま適用しない。利用者が変更した式を無断で上書きせず、現行の対象部品コードを確認する。

## 5. Studioでの安全な適用

1. アプリの名前を付けた保存／複製と、対象部品の変更前コードを保存する。
2. `INSTALL.md`で画面・親・対象名・依存を確認する。プロパティ変更だけなら指定された数式バーで更新する。
3. YAML置換の場合は、確認済みの対象だけを旧親から取り除き、**親を選択して**新しいコントロール定義を貼る。画面直下部品なら画面自体を選択する。
4. 同名衝突による自動改名を確認する。想定外の`_1`等が付いた場合はそのまま続けず、バックアップから戻して対象名と参照を整理する。
5. 元の名前、親、兄弟順、寸法、Visible、依存式、ギャラリー参照を確認する。削除時に参照式が変化していないかも照合する。
6. F5でパッチ固有の操作と回帰試験を行う。失敗時はアプリの複製／保存版から復元する。

コンテナの親だけを「子なし」で置換して子を失う操作、旧部品を残した重ね貼り、名前衝突を放置した運用はしない。

## 6. 検査・トークン節約

- まず基準版と新しい要求を読み、変更ノードだけを編集する。画像base64・変更しないテストデータ・大きな帳票をチャットへ再出力しない。
- 最小単位化で取り残す依存がないかを検査する。名前・型・親・参照・初期化・検索0件・選択保持・開閉の回帰を確認する。
- 構文／ローカル評価／描画モデル／Studio実機を分けて結果を書く。「全件テスト済み」と一括表現しない。
- パッチから完全版を再現できること、管理用／貼付用のChildren一致、変更しない部分の同一性を検査する。
- トークンの厳密な削減率は保証しない。共通親が大きい場合には部品パッチ自体が大きくなるため、プロパティ式の更新を選択する。
