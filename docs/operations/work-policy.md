# ChatGPT Sol Work 運用方針 v1.05

> 対象アプリ：共通（自動テスト／ハンドメイド）

## 1. 方針

本プロジェクトの要件定義、基本設計、詳細設計、Power Apps Source Code形式YAML／Power Fxの開発、静的テスト、レビュー、GitHub反映をChatGPT SolのWorkで行う。

GitHubのmainを共有正本とし、チャット履歴だけを仕様根拠にしない。YAML、Power Fx、要件、設計、テスト仕様、運用方針、進捗、変更履歴はGitHubで管理する。画像、Excel、Word、PDF、HTML原本、検討用資料などGitHubで版管理しない成果物はChatGPT Libraryで保管する。同じMarkdownをGitHubとLibraryの両方で正本として管理しない。Library内に残すMarkdownは参考・検討用・非正本であることを明示する。

新しい作業への着手時に必ず読む範囲は、本章「1. 方針」と[STATUS](../handoff/STATUS.md)の「現在の作業と読取り対象」に限定する。同一作業中は、いずれかが更新された場合だけ該当箇所を再読する。その後、STATUSに記載された対象ソース、要件ID、関連設計、関連テスト、Library資料だけを基本の読取り対象とする。作業中に新しい依存関係や矛盾を発見した場合だけ、必要な資料を追加で確認する。

ユーザーの最新依頼とSTATUSの対象作業が異なる場合は、最新依頼を優先する。STATUSの不一致だけを理由に確認で停止しない。STATUSの不一致の点は実行結果で明示する。継続的な開発作業へ切り替わる場合は、承認済み作業に必要なSTATUSの読取り対象を追加確認なしで更新する。修正方針の承認や範囲外変更の確認は省略しない。調査・レビューのみでファイルを変更しない作業では、STATUS更新を必須としない。

## 2. 役割

| 担当 | 役割 |
|---|---|
| ChatGPT Sol Work | 要件整理、設計、実装、静的検査、自動実行可能な試験、自己レビュー、文書・GitHub更新 |
| ユーザー | 業務判断、仕様変更の承認、本人操作が必要なPower Apps Studio確認、業務受入、リリース承認 |
| GitHub | 正本、版管理、差分確認、復元 |
| ChatGPT Library | GitHubで版管理しない画像・Office文書・PDF・HTML原本・検討資料の保管 |

Library資料の所在、用途、関連機能、読取り条件は[Library資料索引](library-materials-index.md)で管理する。PowerAppsCanvasAppUIに関係するLibrary資料を追加、移動、改名、削除または役割変更した場合は、同じ変更の中でLibrary資料索引を更新する。現在の作業で読むLibrary資料が変わる場合は、STATUSも更新する。

## 3. 実装ルール

- UI成果物はPower AppsのSource Code形式YAMLとPower Fxとする。HTML／Reactによる代替アプリは作らない。
- 利用可能な部品はモダンコントロールを優先し、機能・互換性上の例外を記録する。
- 通常利用者には `.paste.yaml` を案内し、管理用 `.pa.yaml` の画面Childrenと一致させる。
- Classic/Button@2.2.0へ未対応の `AccessibleLabel` を追加しない。
- PDFViewerをGroupContainerの子にしない。対象環境のコントロール版を確認する。
- 初期表示をOnVisible／OnStart／タイマーだけに依存させず、検索0件時に旧職員の詳細や帳票を残さない。
- 実データ、資格情報、環境固有URLをGitHubへ追加しない。試作データは架空とする。
- 画面ソースの版は0.01刻みとし、新版の確認後に旧版をGit履歴へ集約する。
- v1.11をB案＋職員検索サイドバー開閉の完全版とする。v1.12以降は変更コントロール単位の差分配布を原則とする。
- 差分は[コントロール単位差分配布方針](control-diff-policy.md)に従う。コントロール名や変数名を版が変わるたびに一括変更しない。
- GitHubの完全版正本は必要な箇所だけを編集して維持する。全文のLLM再生成や毎回のチャットへの全文掲載を作業要件にしない。

## 4. 作業手順

1. 本章「1. 方針」とSTATUSの「現在の作業と読取り対象」を読み、本章の読取りルールに従って関連資料を確認する。
2. 動作または仕様を変更する場合は、変更要求を該当する要件IDと受入条件へ反映する。
3. 影響する設計、テスト項目、YAML／Power Fxだけを更新する。
4. 動作に影響する変更は、影響ケースと既定スモークを選定して検証する。
5. 文書だけの変更は、リンク、用語、版、記述の整合を確認する。
6. 継続的な開発作業では結果と未実施事項をSTATUSへ記録し、Library資料は本方針「2. 役割」の更新条件に従う。
7. 本番利用可への昇格は、必要な実機確認とユーザーのリリース承認後に行う。

## 5. 検証と確認

[テスト方針](../testing/test-policy.md)と[テスト仕様書](../testing/test-specification.md)は、動作に影響する変更時に適用する。文書だけの変更ではテスト仕様書全体を読まず、リンク・記述の整合を確認し、STATUSの関連テスト欄を「対象外。リンク・記述整合のみ確認」とする。

自動実行可能な静的検査、公開アプリE2E、証跡取得はWorkが実行する。本人操作、業務上の妥当性判断、実機でしか確認できない受入事項はユーザーが担当する。自動化基盤の構築状況と実行結果はSTATUSで分けて管理する。

ローカル検査はMicrosoft公式コンパイラやPower Apps Studioの実行試験ではない。実機確認を行っていない項目を合格と記載しない。検索、ページ移動、対象職員切替、0件、帳票、PDF、画面サイズ、キーボード操作の結果を分けて記録する。

スクリーンショットだけで検索やPDF生成を合格にせず、期待値、実結果、環境、対象版、残件を残す。仕様と実装の矛盾を発見した場合は、関連資料を追加で確認し、GitHubの正本から解決できるか判断する。仕様が明確な実装不具合は修正を継続する。業務判断または仕様変更が必要な場合だけ、STATUSへ記録してユーザーへ確認する。
