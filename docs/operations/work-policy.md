# ChatGPT Sol Work 運用方針 v1.11

> 対象アプリ：共通（自動テスト／ハンドメイド）

## 1. 方針

職員基本テーブル（M_職員基本）の編集を開始するときは、[欠勤時間単価追加タスク #51](https://github.com/hirokazu601218/PowerAppsCanvasAppUI/issues/51) の最新状態を確認する。Openなら同じテーブル編集の計画へ組み込み、実テーブル反映・読戻し確認の証跡を記録してからIssueを閉じる。文書や内蔵コレクションだけの更新では完了にしない。未反映の間はSTATUS先頭の必読部分へタスクを引き継ぐ。

本プロジェクトの要件定義、基本設計、詳細設計、Power Apps Source Code形式YAML／Power Fxの開発、静的テスト、レビュー、GitHub反映をChatGPT SolのWorkで行う。

GitHubのmainを共有正本とし、チャット履歴だけを仕様根拠にしない。YAML、Power Fx、要件、設計、テスト仕様、運用方針、進捗、変更履歴はGitHubで管理する。画像、Excel、Word、PDF、HTML原本、検討用資料などGitHubで版管理しない成果物はChatGPT Libraryで保管する。同じMarkdownをGitHubとLibraryの両方で正本として管理しない。Library内に残すMarkdownは参考・検討用・非正本であることを明示する。

新しい作業への着手時に必ず読む範囲は、本章「1. 方針」と[STATUS](../handoff/STATUS.md)の「現在の作業と読取り対象」に限定する。同一作業中は、いずれかが更新された場合だけ該当箇所を再読する。その後、STATUSに記載された対象ソース、要件ID、関連設計、関連テスト、Library資料だけを基本の読取り対象とする。作業中に新しい依存関係や矛盾を発見した場合だけ、必要な資料を追加で確認する。

ユーザーの最新依頼とSTATUSの対象作業が異なる場合は、最新依頼を優先する。STATUSの不一致だけを理由に確認で停止しない。STATUSの不一致の点は実行結果で明示する。継続的な開発作業へ切り替わる場合は、承認済み作業に必要なSTATUSの読取り対象を追加確認なしで更新する。2026-09-16の指示により、自動化の開始前に最大10工程をこのWorkへ示し、指示された範囲は承認待ちを挟まず開始する。指示範囲外の変更や、判断できない業務仕様は確認する。調査・レビューのみでファイルを変更しない作業では、STATUS更新を必須としない。

職員マスタ検索の画面・機能変更は[単一アプリ運用](single-app-workflow.md)を適用する。継続利用する対象は旧編集用App ID `204a48dc-7f23-43dd-b934-4654a3cfa306` の1件。Codexが隔離データで試験し、同アプリへ保存・公開・Player確認した後、ユーザーが同じPlayerで確認する。追加の配布検証用アプリ・安定版アプリへの移送工程は設けない。旧App ID `362ac991-eead-4f07-8373-afdb3ebfdba1` 向けの自動化は名称変更では対象が変わらないため、対象を新App IDに合わせて安全性を再検証するまで起動しない。

アプリ修正・機能追加の指示を[変更要求](../changes/requests/README.md)へ記録する。自動化フローの実行指示を受けた後は[現行アプリの変更要求から公開・文書反映まで](current-app-request-to-release.md)の順で進め、公開版の照合結果を根拠に要件・基本設計・詳細設計・必要な結合ケース仕様を更新する。総合試験の仕様は[未決事項 D-07](../requirements/open-decisions.md)の判断後に定める。

開始・実行中・終了の報告先は、修正を指示した同じWorkとする。実行中は工程の切替時と長時間処理中に「現在：工程番号／総数・工程名」を提示する。Actionsのjob/step、Issue、取得できたログ等で確認し、状態不明なら最終確認時点と「状況確認中」を明示する。終了・停止時は冒頭で示した全工程について、成功／失敗／対象外／未実施と理由・証跡を表で報告する。具体的な番号・状態・例外処理は[無人修正・テスト公開手順](staff-master-unattended-runbook.md)を正本とする。

## 60分での中断・報告（2026-09-16追加）

Workの作業開始時刻を記録し、60分に達するまでに新規変更処理を止め、状態と再開位置を同じWorkへ報告する。工程別の成功・失敗・未実施とリモート処理の状態を明示する。修復や別runでも開始時刻をリセットしない。再開はユーザー指示後とする。自動化も同じ起算時刻を使い、ジョブ単位のtimeoutだけで全体制限を満たしたと扱わない。既存フローへの機械的な共通期限適用は別途検証し、文書化だけで実装済みとしない。

今回のDataverse移行は工程2以降の通常判断・テスト構築・接続変更を承認済み。追加料金が発生する設定またはセキュリティが弱くなる設定は実施前にユーザー確認する。

## 所有者・専用アカウントの継続承認（2026-09-24）

ユーザーはこのプロジェクト全体で、所有者アカウントと専用アカウントについて、追加料金が発生する契約を除く追加・変更・削除などの操作を承認。Makerの所有者セッション終了と専用アカウントへの切替も承認済み。作業の対象・影響を確認して実施し、結果を記録する。追加料金が発生する契約・購入は実施しない。サービス側の自動承認審査や安全基準そのものはこの文書で変更できないため、操作時に別途求められる確認や本人操作はその基準に従う。

## 2. 役割

| 担当 | 役割 |
|---|---|
| ChatGPT Sol Work | 要件整理、設計、実装、静的検査、自動実行可能な試験、自己レビュー、文書・GitHub更新 |
| ユーザー | 業務判断、仕様変更の承認、本人操作が必要なPower Apps Studio確認、業務受入、リリース承認 |
| GitHub | 正本、版管理、差分確認、復元 |
| ChatGPT Library | GitHubで版管理しない画像・Office文書・PDF・HTML原本・検討資料の保管 |

Library資料の所在、用途、関連機能、読取り条件は[Library資料索引](library-materials-index.md)で管理する。PowerAppsCanvasAppUIに関係するLibrary資料を追加、移動、改名、削除または役割変更した場合は、同じ変更の中でLibrary資料索引を更新する。現在の作業で読むLibrary資料が変わる場合は、STATUSも更新する。

## 3. 実装ルール

- UI成果物はPower AppsのSource Code形式YAMLとPower Fxとする。HTML／Reactによる代替アプリは作らない。
- 利用可能な部品はモダンコントロールを優先し、機能・互換性上の例外を記録する。
- 通常利用者には `.paste.yaml` を案内し、管理用 `.pa.yaml` の画面Childrenと一致させる。
- Classic/Button@2.2.0へ未対応の `AccessibleLabel` を追加しない。
- PDFViewerをGroupContainerの子にしない。対象環境のコントロール版を確認する。
- 初期表示をOnVisible／OnStart／タイマーだけに依存させず、検索0件時に旧職員の詳細や帳票を残さない。
- 実データ、資格情報、環境固有URLをGitHubへ追加しない。試作データは架空とする。
- 画面ソースの版は0.01刻みとし、新版の確認後に旧版をGit履歴へ集約する。
- v1.11をB案＋職員検索サイドバー開閉の完全版とする。v1.12以降は変更コントロール単位の差分配布を原則とする。
- 差分は[コントロール単位差分配布方針](control-diff-policy.md)に従う。コントロール名や変数名を版が変わるたびに一括変更しない。
- GitHubの完全版正本は必要な箇所だけを編集して維持する。全文のLLM再生成や毎回のチャットへの全文掲載を作業要件にしない。

## 4. 作業手順

1. 本章「1. 方針」とSTATUSの「現在の作業と読取り対象」を読み、本章の読取りルールに従って関連資料を確認する。
2. 動作または仕様を変更する場合は、変更要求に該当要件IDと受入条件を記録する。公開前の設計差分を候補として明示する。
3. 影響する設計、テスト項目、YAML／Power Fxだけを更新する。
4. 動作に影響する変更は、影響ケースと既定スモークを選定して検証する。
5. 文書だけの変更は、リンク、用語、版、記述の整合を確認する。
6. 公開後に公開版の読戻しとPlayerを照合し、確認した内容と未確認部分を要件・基本設計・詳細設計・結合テスト仕様へ反映する。継続的な開発作業では結果と未実施事項をSTATUSへ記録し、Library資料は本方針「2. 役割」の更新条件に従う。
7. 本番利用可への昇格は、必要な実機確認とユーザーのリリース承認後に行う。

## 5. 検証と確認

[テスト方針](../testing/test-policy.md)と[テスト仕様書](../testing/test-specification.md)は、動作に影響する変更時に適用する。文書だけの変更ではテスト仕様書全体を読まず、リンク・記述の整合を確認し、STATUSの関連テスト欄を「対象外。リンク・記述整合のみ確認」とする。

現行アプリの改修では[全体テスト計画](../testing/test-policy.md)と[試験選定記録](../testing/change-records/README.md)に従い、改修した各部品の実画面単体テストを必ず選定する。他部品へ影響する場合は結合ケースも選定し、影響しないと判断した場合は理由を残す。既存の自動ケースで十分なら再利用し、不足する場合はコードを追加・更新する。総合テストのシナリオ・実施時期は後続で定義する。旧App IDのActions成功を現行アプリの合格へ転記しない。

自動実行可能な静的検査、公開アプリE2E、証跡取得はWorkが実行する。本人操作、業務上の妥当性判断、実機でしか確認できない受入事項はユーザーが担当する。自動化基盤の構築状況と実行結果はSTATUSで分けて管理する。

ローカル検査はMicrosoft公式コンパイラやPower Apps Studioの実行試験ではない。実機確認を行っていない項目を合格と記載しない。検索、ページ移動、対象職員切替、0件、帳票、PDF、画面サイズ、キーボード操作の結果を分けて記録する。

スクリーンショットだけで検索やPDF生成を合格にせず、期待値、実結果、環境、対象版、残件を残す。仕様と実装の矛盾を発見した場合は、関連資料を追加で確認し、GitHubの正本から解決できるか判断する。仕様が明確な実装不具合は修正を継続する。業務判断または仕様変更が必要な場合だけ、STATUSへ記録してユーザーへ確認する。
