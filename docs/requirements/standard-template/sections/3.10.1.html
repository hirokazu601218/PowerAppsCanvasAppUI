現在の要件

給与班と局担当の対象範囲、業務マスタ管理／システム管理の役割分離を適用する。

要件未設定・判断が必要な内容

本番セキュリティ方針の正式承認、監査・機微情報・脆弱性対応。

具体的な条件・対象範囲・判定基準を未設定のまま表示しています。レイアウト案やテンプレートの例から補いません。

標準テンプレートの補助項目・記入要領 案件の要件とは別

次は公式テンプレートが記入を促す項目です。例文・例示値・推奨条件を、そのまま本アプリの確定要件にしていません。

表の記入項目

表 37　本システムにおけるセキュリティ対応方針

項番 / 分類 / 概要

  • 原則
  • システム特性（概要）
  • 優先的に対処すべきセキュリティリスク
  • セキュリティ対応方針

表内の見本値は本アプリの要件へ採用していません。

原本の記入ガイド

  • 情報システムのセキュリティ要件定義に影響するシステム特性として以下を記載します。なお、別の章で既に記載されているのであれば、本章で改めて明記する必要はありません。 情報システムの利用者（国民or政府系職員orその他） 情報システムで取扱う情報（個人情報、機微情報有無） 利用環境・ネットワーク構成（ネットワーク接続方法（インターネット、専用線、その他）、外部システムとの接続有無）
  • 情報システムにおけるセキュリティ対応方針を検討するため、システム特性を踏まえて、セキュリティリスクを発生確率×影響度で評価し、特にリスク低減を図るべきセキュリティリスクを検討し記載する。リスクについては「どのような脅威により、どのような被害が発生するか」を記載します。リスク評価の詳細な実施方法は以下等を参照してください。 IPA：セキュリティバイデザイン導入指南書（セキュリティ・バイ・デザイン導入指南書 （ipa.go.jp）） IPA：制御システムのセキュリティリスク分析ガイド（「制御システムのセキュリティリスク分析ガイド 第2版 ～セキュリティ対策におけるリスクアセスメントの実施と活用～」を公開：IPA 独立行政法人 情報処理推進機構）※制御システムが対象ですが、情報システムでも考え方は活用可能です。
  • セキュリティ要件を漏れなく導出するためのベースライン（情報システムのセキュリティ標準）を決定します。要件定義の際は、選定したベースライン（システムのセキュリティ標準）に基づいて、自システムの特性やセキュリティリスク等に基づいて要件の追加/削除等を行い、過不足ないセキュリティ要件を導出します。 政府情報システムにおいては以下のベースラインの活用事例が多くあります。※以下以外のセキュリティ標準や、複数組合せて使用することも可能であり、システム特性を考慮して必要なベースラインを選定することが重要です。 情報システムに係る政府調達におけるセキュリティ要件策定マニュアル：政府機関対策関連 - NCO（国家サイバー統括室） CIS Critical Security Contorls：CIS Critical Security Controls （cisecurity.org）
  • 優先的に対処すべきセキュリティリスクに対して、どのようにリスク低減を図るか、記載サンプルに倣って対応方針を記載します。（ある程度具体的な内容を記載頂くことが望ましいです。） その他のリスクへのセキュリティ対応方針については、情報システムにおける全般的セキュリティリスクへの基本的な姿勢について記載します。 以降で定義したセキュリティ要件が、本対応方針に沿っているか検証し、情報システムにおけるセキュリティ対応方針とセキュリティ要件の一貫性を担保することが重要です。 ガバメントクラウドを利用する場合は、セキュリティ対応方針に「ガバメントクラウドの各種ガイドやテンプレートに従い、セキュリティを担保する」といった文言を記載してください。
