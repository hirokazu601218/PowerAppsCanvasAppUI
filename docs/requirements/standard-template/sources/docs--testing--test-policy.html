全体テスト計画

対象：職員マスタ検索の現行単一アプリ／文書版 v2.00（2026-09-26）

1. 位置付け・対象

本書は試験の対象、工程、選び方、役割、判定を定める正本。工程別の詳細は単体テスト計画、結合テスト計画、総合テスト計画を参照する。ケースの操作と期待値はテスト実施要領を参照する。改修ごとの選定は試験選定記録、業務受入は受入テスト計画、自動実行設定は現行アプリE2E運用に分ける。旧テスト方針v1.00は作成当時の記録。

対象環境は StaffMaster-Automation-Test（68e00049-b7e5-eda6-9888-9a3cc493c5be）、対象App IDは 204a48dc-7f23-43dd-b934-4654a3cfa306。アプリの表示名は「自動開発_職員マスタ検索」。職員基本・通勤・基準給与簿の_STUDIO隔離テーブルと隔離HTMLを使用する。単一アプリ運用を優先する。旧App ID 362ac991-eead-4f07-8373-afdb3ebfdba1 向けのpack/import/publish/restoreと旧テストの合格は現行アプリの証跡に転用しない。

参考：デジタル庁 DS-120 デジタル・ガバメント推進標準ガイドライン実践ガイドブック、第3編第7章 Step.3-3「テストの計画を立てる」（2026年7月15日掲載）。DS-120は参考文書。工程の区分を本プロジェクトのPower Apps改修に合わせて適用する。

2. リスクと重点

リスク 優先して確認する結果
職員の取り違え 検索結果から選択した番号・氏名が詳細、履歴、帳票で一致
隔離外への書込み・旧App IDの誤操作 接続先、実行App ID、読取り専用試験、変更対象を照合
認定簿の誤差込・保存漏れ 2ページの内容と出力ファイルの実体、失敗時の復帰を照合
表示の欠落・操作不能 対象画面と変更した部品を実画面で操作し、可視値を確認

変更内容によってテスト範囲と証跡の濃淡を決め、選定記録に理由を残す。重大なリスクへの影響を理由なく省かない。静的検査やコードレビューは実画面の結果の代わりにならない。

3. テスト工程の選び方

工程 対象と開始条件 合格に必要な観測 実施タイミング
単体テスト 改修した部品・数式は必ず対象。対象App IDと隔離データ、期待値を確定 公開Playerでその部品を実際に操作し、当該部品の入力から結果まで照合。直接操作できない部品は最小限の画面操作で結果を確認 改修ごと
結合テスト 改修部品が他部品、複数部品、画面、データ、帳票、外部連携へ影響する場合 間の受渡し、状態、異常時動作と結果の整合を確認 影響がある改修ごと。影響なしの判断理由も記録
総合テスト 複数機能を通す業務シナリオと開始・終了条件が定義されてから 業務の一連の結果と必要な非機能要件 シナリオと実施時期は後続で策定。一括PASSにしない
受入テスト 対象機能の試験結果・残件が提示された後 ユーザーが業務目的、操作性、期待値を自身で確認 別計画に従う

従来のL0～L4は確認手段の区分であり、単体・結合・総合という工程と一対一に対応しない。ソース静的検査、Studioの式エラー確認、公開版照合、Playwrightの操作を工程に応じて組み合わせる。公開直後の起動確認を実施しても総合テスト完了とは扱わない。

4. 設計成果物と観点の対応

工程 主な入力 観点と記録先
単体 変更したPower Fx・YAML、部品仕様、詳細設計 入力・分岐・結果、エラー。変更部品と単体ケースIDを記録
結合 詳細設計、部品間参照、画面遷移・データ契約 関連部品への反映、例外、隔離接続。影響判定と結合ケースIDを記録
総合 基本設計、業務フロー、機能・帳票一覧 業務シナリオの組合せと非機能。対象シナリオは後続で策定
受入 要件定義、業務要件、ユーザーが期待する操作 業務遂行の可否、操作性、未解決事項。受入計画に記録

既存コードが選定ケースを十分検証できるなら再利用する。新しい分岐、期待値、連携が漏れる場合は追加・更新する。失敗回避のために期待値を緩めない。公開版とGitHub候補ソースの一致が照合できない場合は「公開Playerの現状試験」と記録する。

5. 担当、環境、証跡

Codexは影響分析、ケース選定、テストコードの保守、実行と一次評価を担当。GitHub Actionsは選定記録の形式・差分・ケース参照を検査し、選定された自動ケースを実行する。ユーザーは業務上の期待値と受入可否を判断する。Actionsの静的チェックは影響分析の漏れを意味的に検証できない。

各改修では変更パス・部品、対象App ID、影響先、単体ケース、必要な結合ケース、総合テストの扱いを選定記録に記録する。実行後は実施記録の様式にrun URL、コミット、公開版の照合状況、日時、環境、ケースID、期待値、実測値、PASS/FAIL/BLOCKED/NOT_RUN、残件を残す。GitHubには架空データだけを置き、資格情報、認証状態、機密を含むtraceは保存しない。画面やPDFの証跡はリスクに応じて選ぶ。

6. 合否、中断・再開

PASSは指定アプリ・公開版で期待値と必要証跡を確認した状態。FAILは期待値と不一致、BLOCKEDは認証・環境・データ等で判定不能、NOT_RUNは未実施。再実行成功だけで不安定な試験を完了扱いしない。

認証失敗、App ID不一致、隔離データの不明な変更、ケース設計の多数の誤り、共通部品の不具合の影響範囲不明があれば対象試験を中断する。原因、修正内容、影響範囲、再テスト対象、環境を確認して再開する。改修部品の単体ケース、必要な結合ケースが未実施なら改修完了としない。総合テストと業務受入はそれぞれ独立して判定する。

7. 現時点の実装境界

現行アプリ向け新しいActionsとE2Eは、実環境で認証・操作・結果を確認してから稼働済みと記録する。既存のハンドメイド版無人E2Eと旧95項目の設計・履歴は現行アプリ全件自動化済みの証拠にならない。総合テストのシナリオ・実施時期は未決。自動配布や本番データへの切替は本計画の対象外。
