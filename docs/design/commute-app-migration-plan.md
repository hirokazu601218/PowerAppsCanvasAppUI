# 通勤データ取得元切替：権限確認と再開計画

> 2026-09-17更新：以下は承認前の移行計画です。その後、ユーザー承認によりRead追加・接続・Studio修正・公開まで実施済み。現在の結果は[通勤v1.18結果](../testing/commute-v1.18-results.md)を参照してください。

2026-09-17。今回の依頼は内蔵通勤データ削除、Power Fx整理、Dataverse通勤参照、認定簿の実機検証、合格後公開。公開版v1.17を確認した段階で、利用者の権限不足を検出したため反映を停止した。

## 確認結果

[読取り監査run 35166791941](https://github.com/hirokazu601218/PowerAppsCanvasAppUI/actions/runs/35166791941)で、専用利用者 `powerapps-test@govaca.onmicrosoft.com` をメール完全一致・有効ユーザー1件で照合した。直接割当は `StaffMaster Test Reader`。チーム継承も含むRetrieveUserPrivilegesで、職員基本のReadはGlobal、通勤のReadは未付与だった。

[割当範囲再確認run 35166925612](https://github.com/hirokazu601218/PowerAppsCanvasAppUI/actions/runs/35166925612)で、既存Readerロールは対象ユーザー1名・チーム0のみへの割当と確認した。記録：[監査JSON](../testing/commute-access-audit.json)。

現行アプリの通勤5件はApp.FormulasのStaffCommuteHistoryにあり、認定簿の共通日付・経路等はStaffLedgerTemplateに残っている。後者もDataverseの選択レコードから生成する必要がある。

## 承認を求める変更

既存隔離テスト環境の `StaffMaster Test Reader` へ、T_通勤のReadだけをGlobal（この環境内の当該テーブル全件）で追加する。対象は専用テスト利用者のみであることを再確認してから適用する。詳細は [提案JSON](../../automation/commute-read-permission-proposal.json)。現時点ではapproved=false、未適用。

通勤の6件はAutomationが所有しており、ユーザー自身の所有行だけを読めるBasicでは足りない。環境をまたぐ権限・管理者権限・更新権限は追加しない。ライセンス購入や課金設定の変更は提案に含まない。

ユーザーの「権限変更や追加料金が発生しなければ最後まで」を停止条件として扱う。以前のM_職員基本の読取り承認を、新しい通勤テーブルへの承認と取り違えない。

## 承認後の実装対象

1. 利用者の通勤読取りだけを追加し、職員基本・通勤の実効特権と6件へのアクセスを再確認。
2. Studioに既存DataverseのT_通勤を追加。現行v1.17パッケージを保全してv1.18候補として修正。通勤Lookup・論理名・日付型を接続済みStudioで確認。
3. StaffCommuteHistoryの内蔵5件とStaffLedgerTemplateの合成値を削除。JSON正本とrender_staff_history.pyも対象種類の生成を廃止する。勤務・保険・税・給与簿の内蔵データは維持。
4. 選択職員に対応するDataverse通勤レコードを取得。親Lookupと職員番号を取り違えず、全件ForAll読込を避けて委任可能なFilterから作る。複数の認定レコードを選択できるようにし、認定簿は同じ選択レコードの日付・経路1～4・定期/回数券金額・月額合計を表示する。
5. 認定簿表示ボタンの現在のLookUpによる先頭1件決め打ちを解消。0件・選択職員変更・再読込で前の認定簿やPDFを使い回さない。任意NULLは空欄、金額0は0を表示する。
6. 日付・2～4経路目の原本名称の意味を勝手に変えず、値を対応する表示項目へ移す。原本にない新幹線等の項目に架空の値を補わない。
7. Studioでコンパイルとプレビュー確認。専用ユーザーで0/1/複数件・同姓同名・全6認定IDの表示を確認し、PDFのA4横2ページと既存検索・給与等の回帰を実施する。
8. 合格後に公開し、公開版の同じデータと認定簿を再検証。接続済みパッケージを保存し、旧接続を前提とする検証基準を正式な新接続へ更新する。
