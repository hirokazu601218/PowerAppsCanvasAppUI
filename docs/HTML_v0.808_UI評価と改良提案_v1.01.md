## 1. 結論

**「左で職員を選び、右で表を確認する」という骨格は良い設計です。一から別の画面にする必要はありません。改良すべきなのは、情報の優先順位、文字の読みやすさ、操作と状態の分かりやすさです。**

現在の画面は、Excelや給与項目に慣れた担当者が情報を照合する用途には適しています。一方、全分野の履歴を連続して並べるため、初めて使う人には見る場所が多く、熟練者にも縦横のスクロールが負担になります。

推奨案は、左の検索・一覧を維持し、右側を「職員ヘッダー＋概要＋業務別タブ」にする構成です。**項目は削除せず、概要・全項目・履歴・帳票に表示場所を分けます。** 分野をまたぐ照合には「全分野を比較」を設け、タブの切替を何度も繰り返さずに確認できるようにします。

## 2. 評価方法と限界

HTMLのCSS、表の生成処理、検索・選択・出力・モーダルの処理を確認し、会話中の元HTMLの画面画像と照合しました。比較基準は、DADS、MicrosoftのCanvas／Fluent系コントロール、IBM Carbon、Nielsen Norman Groupのユーザビリティ原則です。

以下の点を区別します。

- **確認事実**：ソースに記載された文字サイズ、列構成、イベント処理、色など。
- **専門的判断**：情報密度や認知負荷、移植時の難易度の評価。
- **未検証**：実利用者によるタスク試験、接続先を含むブラウザー実行、スクリーンリーダー、Power Apps実機、帳票のPDF生成。

点数は5段階の相対的な専門家評価です。5＝十分良い、4＝概ね良い、3＝改善余地あり、2＝大きな改善が必要、1＝目的達成が難しい。正式なアクセシビリティ適合判定や利用者満足度の測定値ではありません。

なお、これまでのYAMLで起きた初期化漏れや不正プロパティは、移植実装側の問題です。それをそのままHTMLのUIの欠点として採点していません。

## 3. 指定された7つの評価軸

| 評価軸 | 現状 | 良い点 | 課題と判断 |
|---|---:|---|---|

| ユーザーライクな画面か | 3/5 | 件数、選択行の強調、在籍状態、出力ボタンがある | 全履歴が同じ強さで並び、今何を確認する画面か分かりにくい。検索結果と選択職員が食い違う可能性もある |

| 拡張性 | 2/5 | データ列の抽出など、未知の項目を表示する工夫はある | 業務や項目を増やすほどページと表が長くなる。HTMLの動的列追加をCanvasへそのまま移すのは難しい |

「見た目が今風だから優れている」とは評価していません。給与担当者が、対象職員を間違えず、現行・過去・将来を識別し、数値を速く照合できることを重視しています。

## 4. ソースから確認できた具体的な問題

### 4.1 文字サイズと情報密度

| 対象 | HTMLでの指定 | 評価 |
|---|---|---|
| 一覧・履歴表 | 12px | 長時間の照合、画面縮小、視力が弱い利用者には小さい |
| 入力欄・ボタン | 13px | 表との区別はあるが、十分な操作性を一律に保証する大きさではない |
| セクション見出し | 14〜15px | 大量の表の中では見出しの階層が弱い |
| 職員名 | 24px | 対象者の識別には有効。維持する |
| アプリタイトル | 18px | 適切。主たる業務情報より過度に目立たせる必要はない |

12pxであることだけでWCAG違反と断定はできません。ただし、読みやすさと拡大時の操作性を考えると、本文は見かけ上16px程度を初期値とし、補足14px、見出し18〜20pxを提案します。これは本画面向けの提案値であり、DADSやWCAGの一律規定値ではありません。

### 4.2 横幅とスクロール

- 左ペインは400px固定。右側の基本情報は3組の「見出し＋値」を横並びにし、見出し側が130px固定です。中程度の画面幅では値側が狭くなります。
- 履歴表の見出しは原則折り返さず、給与の主要金額列は145px、備考は200pxです。列数が増えると横スクロールが長くなります。
- 左ペイン、右ペイン、個別の表、モーダルにスクロール指定があり、ポインター位置によって動く領域が変わります。
- 1000px以下で1列へ切り替えるCSSはあります。「スマホ対応が全くない」わけではありません。ただし1001〜1199pxでは1200pxの最小幅が残り、狭い画面で横にはみ出す条件があります。

改良では左幅を340〜380px程度、右側を可変とし、検索部分・職員ヘッダー・操作バーを固定、一覧と詳細本文をそれぞれスクロール対象にします。広い表は「全幅表示」に切り替え、ページ全体の縮小で解決しない方針です。

### 4.3 検索結果と選択職員の不一致リスク

`doSearch()` は絞込結果を更新しますが、`state.selected` を検索結果に合わせて更新しません。`selectedMaster()` は絞込結果ではなく職員マスタ全体から選択職員を探します。

このため、**Aさんを選択した後、Aさんを含まない条件で検索しても、右側にAさんの詳細が残る条件があります。** 検索結果が0件でも同じことが起こり得ます。これは外観の問題より優先して直すべき対象者誤認のリスクです。コード上の状態遷移からの判断であり、接続済みブラウザーでの再現試験は未実施です。

推奨ルール：選択職員が結果内に残るなら選択を維持し、結果外なら選択解除。0件時は明示的な空状態にする。1件の場合に自動選択するなら、そのルールを統一する。

### 4.4 キーボードとフォーカス

- 職員一覧の行は `tr` の `onclick` で選択しています。この行に対応するTab停止やEnter／Space操作が、確認した一覧生成・イベント登録処理にはありません。
- モーダルには `role="dialog"`、`aria-modal`、ラベル、開いた際のフォーカス設定、Escapeで閉じる処理があります。アクセシビリティ配慮が全くないわけではありません。
- 一方、外側モーダル全体のフォーカス閉じ込め、閉じた後の元ボタンへの復帰、背景のキーボード操作抑止は十分に確認できません。内側のフロー案内には一部フォーカス復帰があります。
- `draw()` は検索・一覧・詳細のDOMをまとめて作り直すため、選択前のスクロール位置やフォーカスが失われる可能性があります。

Canvasでは単なる透明なクリック領域を増やすのではなく、行の意味を読み上げられる選択操作を用意します。HTMLのARIAをCanvasへ機械的に写すのではなく、コントロール固有のアクセシビリティ機能を確認します。[Microsoft：アクセシブルなコントロール構成](https://learn.microsoft.com/en-us/power-apps/maker/canvas-apps/accessible-apps-structure)

### 4.5 状態・空欄・エラーの伝え方

- `periodClass()` により現行・過去・将来の行が緑・灰・青になりますが、履歴表の標準行には「現行」「過去」「予定」という状態ラベルが追加されません。日付を読むことはできますが、色の意味を即座に理解しにくい構成です。
- 空欄は、未登録・該当なし・未取得・期限なしを区別しにくい表示です。
- 上部に出力結果を表示する領域はありますが、職員検索・データ取得・PDF作成の状態表示を統一する余地があります。
- ヘッダーの長い元ファイル名は管理者には有益ですが、利用者の主作業を圧迫しています。

改良では状態を文字と色で併記し、未登録・該当なし・取得失敗を区別します。ただし、元データに区別する情報がなければ勝手に推定せず「情報なし」と表示します。

### 4.6 色のコントラスト

以下はCSSの単色同士をWCAGの相対輝度式で計算した値です。実画面のすべての重なり、無効状態、フォーカス状態を測定したものではありません。

| 組合せ | コントラスト比 | 判断 |
|---|---:|---|
| 濃紺 `#073B78`／白 | 11.02:1 | 良好。維持できる |
| 本文 `#1F2937`／白 | 14.68:1 | 良好 |
| 補足 `#4B5563`／白 | 7.56:1 | 良好 |
| 緑 `#16833A`／白 | 4.84:1 | 通常文字4.5:1の目安を満たす組合せ |
| 境界線 `#CBD5E1`／白 | 1.48:1 | 入力欄の識別に必要な唯一の境界である場合は弱い |

通常文字の4.5:1、操作部品の識別に必要な視覚情報の3:1を目安に検証します。装飾の罫線まで一律に3:1を要求するものではなく、大きな文字・非活性部品等には基準上の例外があります。[WCAG：文字コントラスト](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)、[WCAG：非テキストのコントラスト](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)

## 5. 広く使われる良い業務UIとの比較

「世界で最も良いUI」の順位付けではなく、公開された業務UIの設計原則と比較します。

| 比較対象 | 参考にする考え方 | 現HTMLとの比較・採用案 |
|---|---|---|
| DADS：テーブルコントロール | 検索・件数・表示件数・出力等をテーブル周囲に整理 | 現状の検索・件数・ページングは方向が合う。表示設定と出力対象をさらに明確化 |
| DADS：タブ | 同じ職員について、異なる観点を切り替える | 業務別の詳細切替に適する。ただし分野横断比較をタブだけに閉じ込めない |
| IBM Carbon：Data table | 表内の比較、表の操作バー、行の詳細展開、密度と横幅の管理 | 表そのものは残す。多数の小さなカードへ全面置換せず、主要列＋詳細を採用 |
| Microsoft：Fluent系Data Grid | 行列形式、検索・並べ替え・選択を標準部品で扱う | 自作セルの量を減らす候補。利用環境の部品提供状況と列・スタイル機能の確認が必要 |
| Nielsen Norman Group | 状態が分かること、利用者の言葉、初心者と熟練者の両立、誤操作防止 | 基準日・検索対象・出力対象を明示し、概要と詳細を分け、対象者の取り違えを防ぐ |

参照：[DADS テーブルコントロール](https://design.digital.go.jp/dads/components/table-control/)、[DADS タブ](https://design.digital.go.jp/dads/components/tab/)、[Carbon Data table](https://carbondesignsystem.com/components/data-table/usage/)、[Microsoft Data Grid](https://learn.microsoft.com/en-us/power-apps/maker/canvas-apps/controls/modern-controls/modern-control-data-grid)、[NN/gの10原則](https://www.nngroup.com/articles/ten-usability-heuristics/)。

タブは同時比較に弱い点もあります。DADSでも、複数セクションを同時に開いて比較する場合はアコーディオンを案内しています。本提案の「全分野を比較」はその弱点を補うためのものです。[DADS タブの注意点](https://design.digital.go.jp/dads/components/tab/)

## 6. 改良後の画面構成

### 6.1 残すもの／変えるもの

| 残す | 変える |
|---|---|
| 左の職員検索・一覧、右の職員詳細 | 左の検索を固定し、一覧のスクロールと分離 |
| メイリオ系、濃紺・白・淡い灰青 | 本文の可読性を上げ、装飾の罫線と操作部品の境界を区別 |
| 表による日付・金額・条件の比較 | 概要は主要項目、業務別タブは全項目・全履歴 |
| 選択行の強調、在籍状態、件数 | 選択・検索中・0件・取得失敗の状態を統一 |
| 元の全業務項目と帳票様式 | 情報を配置する階層と出力の動線 |

### 6.2 画面イメージの読み方

別途作成する画像は、**PC用の「概要」タブを選択した状態**です。全業務の全項目を画像1枚へ詰め込むものではありません。画像に見えていない項目は下記の詳細タブで保持します。画像中の人物・数値は架空データです。

| 領域 | 内容 |
|---|---|
| 最上部 | アプリ名、「参照用」「テストデータ」、取得日時、データ情報、使い方 |
| 左上 | 氏名・職員番号等の検索、所属・在籍状態、検索、クリア。検索対象の補足 |
| 左下 | 件数、並べ替え、職員一覧、選択表示、ページ操作、検索結果のExcel出力 |
| 右上の固定部 | 職員名・職員番号・所属・在籍状態。表示密度、全分野比較への切替 |
| 右側のタブ | 概要／給与・勤務／通勤／社会保険／税・控除／基準給与簿 |
| 概要本文 | 基本情報、現行給与・勤務、現行通勤支給予定、社会保険・税控除の要約 |
| 通勤の操作 | 「認定簿プレビュー」。対象レコード確認後、帳票表示とPDF出力 |

### 6.3 項目を削らない移行先

| 元HTMLの情報 | 改良案での表示場所 |
|---|---|
| 職員基本情報9項目 | 概要の基本情報。職員名等はヘッダーにも表示 |
| 給与・勤務条件履歴 | 給与・勤務タブ：主要一覧＋行の全項目詳細。現行・過去・予定を選択可能 |
| 通勤支給予定、各月金額、IC運賃等 | 通勤タブ：支給予定の全項目、月別表示、認定レコードの選択 |
| 社会保険履歴 | 社会保険タブ：全項目・全履歴 |
| 住民税履歴 | 税・控除タブの「住民税」区画。税・固定控除とは明確に分ける |
| 税・固定控除設定履歴 | 税・控除タブの「税・固定控除」区画 |
| 基準給与簿の要約列と全詳細列 | 基準給与簿タブ：要約一覧＋全項目の分類別詳細／全幅表／Excel出力 |
| 認定簿の2枚の様式 | 認定簿プレビュー。画面用UIの基準で帳票の罫線・項目を変更しない |

全項目を残すことと、すべてを最初から同じ画面に出すことは別です。見たい項目が「隠されていて存在に気付けない」状態を防ぐため、詳細へのリンクには項目群の名前を付けます。

### 6.4 初心者と熟練者を両立する方法

- 初心者：概要を初期表示。「現行」「未登録」などを文字で表示し、専門用語には短い説明を用意。次の操作を職員選択→業務確認→帳票確認の順に見せる。
- 熟練者：前回のタブ・表示密度を保持し、主要列／全項目、並べ替え、条件保存を用意。全分野比較で元画面に近い連続確認もできる。
- 共通：表示密度は行の余白を中心に変更し、コンパクトを選んでも文字を極端に小さくしない。初期値を勝手に「在籍のみ」にして退職者を見失わせない。
- 職員切替時：選択職員は変えるが検索条件と一覧のスクロール位置は保持。検索結果外となった職員の詳細は解除する。

## 7. Power Appsでの実装方針

| 部位 | 第一候補 | 作りやすさ・留意点 |
|---|---|---|
| 外枠・左右分割 | 自動レイアウトコンテナ | 親幅・高さに追従。固定座標の積み重ねを減らす |
| 検索・条件・操作 | モダン入力・選択・ボタン | 利用環境で提供される部品を優先。未対応プロパティを推測でYAMLへ書かない |
| 左の職員一覧 | Gallery、または利用可能なData Grid | 小さな一覧では氏名・番号が読める列幅を確保。行選択の読み上げとキーボード操作を検証 |
| 右の基本情報 | Label等を自動レイアウトで配置 | 画面幅に応じて3組→2組→1組へ変更 |
| 履歴表 | モダンData Gridを試験採用 | 使えない環境や必要な表現ができない箇所はGalleryによる共通表。すべてをセル単位で別実装しない |
| 業務別タブ | 利用可能なタブ部品＋表示領域 | 自作ボタン列の場合は、選択状態・フォーカス・操作順も設計する |
| 帳票 | 画面表示領域とPDF用領域を分離 | 画面の検索・ボタンをPDFへ混ぜない。正式運用は改ページ・フォント・保存権限まで検証 |
| 色・寸法 | Power Fxトークン | 管理値を共通化。ただしコントロールごとの文字サイズ単位・描画差を確認 |
| データ | 試作はテストデータ、本番はDataverse等 | UI表示用の文字列と保存用の型を分離。全データ一括取得を前提にしない |

## 9. アクセシビリティと検証の基準案

1. 本文は見かけ上16px程度、補足は14pxを初期設計値とする。主要操作は高さ44px程度を確保する。44pxは本案件の操作性目標であり、WCAG 2.2 AAの一律最低値ではない。WCAG 2.5.8の最低ターゲットサイズは原則24×24 CSS pxで、間隔等の例外条件がある。[WCAG ターゲットサイズ](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
2. 操作部品のフォーカス枠を視認でき、選択状態は色・文字・位置の複数で分かるようにする。
3. ラベルと値、表の行・列、現在の選択職員がスクリーンリーダーで理解できるか確認する。表風Galleryは見た目だけで表の読み上げ機能を保証しない。
4. モーダルを使う場合、背景への操作を止め、開く際と閉じる際のフォーカスを管理する。実装上確保できない場合は専用画面へ切り替える。PDF Viewerの親子制約にも注意する。
5. 1366×768と1920×1080で初期・長い氏名・長い所属・複数履歴を確認する。文字拡大200%とキーボード操作も別途試験する。2次元の表に必要な横スクロールまで一律に禁止しない。
6. PDFは画面のアクセシビリティとは別に評価する。帳票背景を画像にすると正確な外観に寄せやすいが、文字の検索・コピー・読み上げ・タグ付きPDFを保証できない。

帳票の2枚を縦につなぐプレビューは、現在の作業習慣を維持する選択肢です。ただしDADSの一般的な短い確認ダイアログと同じ扱いで「準拠」とは表現しません。長い閲覧や複雑な操作には専用プレビュー画面の方が保守・アクセシビリティ上扱いやすい場合があります。[DADS モーダルダイアログ](https://design.digital.go.jp/dads/components/modal-dialog/)
